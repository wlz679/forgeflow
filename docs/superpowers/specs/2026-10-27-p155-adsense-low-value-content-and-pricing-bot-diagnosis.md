## 4. 结论

**「低价值内容 = 因为 v1 是纯计算」这个前提不成立，且「做完 2.0 灵魂改造就会好很多」的推论也不成立。**

对照政策三条：

| 政策条目 | 实测 | 结论 |
|---|---|---|
| ① 提供真实、高质量的信息、工具或服务 | 每页 1,900–3,200 词、77% 页面特有、v3 板块已上线 | **达标** |
| ② 持续精选优质内容和维护网站页面结构 | **198 个索引 URL 硬 404（19% 展示）** + history/favorites 空壳页被索引 + 根页无 title/canonical | **不达标（可修）** |
| ③ 能够切实引起并持续吸引用户关注 | **20 次点击 / 92 天**；68% 的查询排在第 5 页以后 | **不达标（长线）** |

**⇒ 判定主体是 ② 和 ③，不是 ①。**

- **② 是结构问题，1 天能修完**，而且有 2,526 次展示的实测量撑着。
- **③ 是排名问题**：站点已被 Google 收录并展示 9,554 次，但平均排名 29.6 ⇒ **加更多页面、加更多板块都不会改善平均排名，反而摊薄权重**。真实杠杆是「让已有页面在已有查询上往前挪」+「把 19% 死链的权重救回来」+「品牌词排第 1」。
- **2.0 灵魂改造仍然值得做，但落点必须重定**：从「437 页各加板块」改成「**只投给贡献 80% 展示的页面**」，且产出必须是**页面独有的结论**（最新模型实价对比、真实行业阈值、跨引擎对比），不是模板句。**给 437 页加统一板块会把相似度推高，反而更像规模化内容滥用**（政策链接里的《适用于 Google 网页搜索的垃圾内容政策》正是这条线）。
  - ⚠️ **这个清单的数字在本轮落地方案里重算过一次**：早先写的「59 个贡献 80% 展示的页面」是**混用分母**算出来的 —— 拿**图表表**的 9,554 当分母，去累加**网页表**的展示（合计 13,383）。两个表本来就对不上（差 40.1%，原因未查明），拿其中一个当另一个的分母，得到的比例没有意义。
  - **口径统一后的权威数字**（清单落在 `src/data/priority-pages.ts`，常量写死并由守卫钉住）：
    | 量 | 值 |
    |---|---|
    | 网页表 URL 行数 | 645（apex + www 各占一行：24 组；带/不带尾斜杠另有 56 组） |
    | 按 pathname 聚合后 | **565 个页面**，展示合计 **13,383**（0 丢失） |
    | 404（已删除的 blog 面） | **179 个页面 / 2,526 次展示**，**全部**能映射到活着的目标页（0 个映射不到） |
    | 活页（含归并进来的展示） | 402 个页面 / 13,383 次展示 |
    | 壳页（noindex，排除） | 4 个页面 / 219 次展示 |
    | 候选页（分母） | **398 个页面 / 13,164 次展示** |
    | **P1（50% 展示）** | **38 个页面** |
    | **P80（80% 展示）** | **117 个页面**（10,557 次展示 = 80.2%） |
    | 117 页的构成 | 工具页 71（去重 53 个 slug）/ 分类页 19 / 主题页 22 / 首页 2 / 静态页 3 |

**是否申请重新审核**：政策页明确给了「解决该问题后可以申请审核」的入口。**建议先做 §3.3 / §3.4 / §3.5 的结构修复，再勾选申请** —— 现在勾"已解决"不成立；且这批修复同时救回 2,526 次展示与品牌词排名，是**同一批改动两处收益**。

**诚实边界**：即使全部修好，0.22 次点击/天的流量也很难支撑有意义的广告收入。**「通过审核」和「有广告收入」是两件事**，前者可达（结构修好后有实据可陈），后者是长线。

### 5.1 信号 E / D 的收口（P156，2026-10-28）

§5 的信号 D 与信号 E 在 P156 合并处理，因为它们是**同一个 bug 的两面**。

**取证（全部来自真实产物，不是读源码猜的）**：

| 量 | 实测 | 出处 |
|---|---|---|
| 数据集模型数 | 245（openai 138 / anthropic 28 / google 67 / deepseek 12） | `src/data/ai-pricing.json`（bot 同步后） |
| 交互态模型数 | 44（openai 18 / anthropic 13 / google 8 / deepseek 5） | `scripts/codegen-customfn.mjs` 的 `popularKeys` |
| 对比页交互态 | 4（每 provider 一个旗舰） | 同上 |

| openai 页**内联客户端表**的模型数 | **18** | 同上（`M['...']=` 表） |

**结论**：信号 D 说的「Cost Comparison (137 Models) 的大列表」与信号 E 说的「数据集 244 vs 交互态 44」，其实是**同一处口径分裂**：构建期 `calculate()` 遍历**全量数据集**，客户端 customFn 只带**交互态白名单**。于是同一页渲染出两套数据，静态正文多报一个数量级；而每周 bot 同步一次，这个差距还会**再大一点**（244 → 245 → …）——所以它是结构性的，不是偶发。

**P156 的处置**（用户 2026-10-28 拍板「只统一文案口径、交互态维持 44」）：

1. 白名单提到单一真相源 `src/data/ai-pricing-popular.json`，`scripts/codegen-customfn.mjs` 改为**读**它（不再各写一份）。
2. 五个 AI cost 引擎的构建期模型集 == 交互态 ⇒ 静态正文与客户端表读同一份数据 ⇒ 静态正文改写 "Cost Comparison (18 Models)" / "Comparing 4 models across 4 providers"。
3. 对比页的关键洞察**未受损**：「🏆 Cheapest Model Overall」在 245 个里是 Gemini 1.5 Flash，而 `gemini-1.5-flash` 正是四个旗舰之一 ⇒ 答案不变。
4. 守卫：`ai-cost-scope-guard`（source-only）+ `ai-cost-scope-build-guard`（build-dep，直接读 dist/ 的 HTML）；变异台子 7/7 KILLED。

**副作用（对 AdSense「低价位内容」有利）**：openai 页可见正文 20,718 → 17,126 字符、静态块 7,026 → 3,434；对比页整页 189,379 → 136,820 字符（-28%）、可见正文 24,149 → 16,010（-34%）、静态块 10,629 → 2,490（-77%）。

**已知取舍**：那 120 行「够不着的长尾价格行」（如 "GPT 4o Transcribe"）从可见正文归零。这是**有意的** —— 它们是静态表里有、交互态选不了的行；换成 2.0 的**页面独有结论**才是正解。**若要保留长尾价格面**，正确做法是在 2.0 批次里给这批页面单独补「按模型查价」的**交互**入口，而不是把静态大表留着。

### 7.2 旧写法有两处结构缺陷

1. `gh pr view "$BOT_BRANCH" ... 2>/dev/null` —— **stderr 被直接丢掉**。gh 的真实报错（403 / 权限 / 配额 / 参数错）一行都不会出现在任何地方，只剩一个裸的 `exit code 1`。
2. 用 `gh pr view` 的**退出码**当"有没有 PR"的判据 —— gh 在"没有 PR"和"API 拒绝访问"两种情况下的退出码无法区分 ⇒ "API 报错"会被误判成"没有 PR"，继而走进 `gh pr create`，再撞一次墙。

**这也解释了为什么这次排查取不到日志**：job log 需要登录态（GitHub 未认证访问返回 403），公开 API 只能证明"分支推了、PR 没建"。

### 7.3 修法

- 诊断写进 **job summary**（Actions 页面直接可见，不需要读 log）：`gh auth status` + `repos/$REPO/actions/permissions` + `repos/$REPO/actions/permissions/workflow`（后者的 `can_approve_pull_request_reviews` 正是"仓库是否允许 GITHUB_TOKEN 建 PR"的那个开关）。
- 存在性判定改用 **API 列表** `pulls?state=open&head=owner:branch`（空数组 = 没有 PR，非零退出 = API 真的报错）。
- 创建/更新后**用 API 回读确认** PR 真的可见，确认不了就非零退出。
- 创建失败时**留下人工可点的 compare 链接** —— 分支已经推了，一周一次的定价增量不该因为建不了 PR 而静默丢掉。

### 7.4 守卫

`tests/sync-pricing-pr-step-guard.test.ts`（source-only，7 条断言）钉住上面 5 条性质。变异台子 **7/7 KILLED**，还原后 sha256 逐字节一致。

## 9. 结构修复的落地方案：三个坑，每一个都差点静默上线

用户 2026-10-28 拍板：**结构修复三项全做**（① 196 个 blog URL → 301 回工具页；② 壳页 noindex + 移出 sitemap；③ 根页补 title/canonical/hreflang/可见内容），**2.0 落点重定**，修复合并上线后再申请复审。**不碰任何 calc 正文，只动 URL 与索引规则。**

实现过程中有三个坑。它们的共同形状是：**构建 exit 0、测试全绿、线上却是坏的** —— 也就是说，任何只盯"构建成功"的门禁都看不见它们。

### 9.1 坑一：`_redirects` 对 Pages Function 处理的请求不生效

Cloudflare 官方文档（[Redirects](https://developers.cloudflare.com/pages/configuration/redirects/)）原文：

> Redirects defined in the `_redirects` file are **not applied to requests served by Pages Functions**, even if the Function route matches the URL pattern. If your Pages application uses Functions, you must migrate any behaviors from the `_redirects` file to the code in the appropriate `/functions` route, or **exclude the route from Functions**.

本站 `dist/_routes.json` 是 `"include": ["/*"]` ⇒ 所有请求都归 Function ⇒ `_redirects` 里的规则**永远不会被执行**。文档给的两条出路：把行为搬进 Function，或把路由从 Function 里 exclude 掉。**本轮选了前者**（把路由做成按需渲染，行为放 middleware）。

### 9.2 坑二：middleware 对预渲染路由不执行

第一版实现把 301 放在 `src/middleware.ts`。构建产物里 middleware **确实被打包了**（`dist/_worker.js/_astro-internal_middleware.mjs` 里能看到完整的正则与 `context.redirect(target, 301)`），但：

- Astro 的 middleware 只在**按需渲染（`prerender = false`）**的路由上于请求期运行；
- 本站是 `output: 'hybrid'` 且**所有页面都是预渲染的** ⇒ `/en/blog/*` 在站内**没有任何页面**，落进 **预渲染的** 404 路由 ⇒ middleware 根本不参与。

**实测**（`wrangler pages dev` 真 HTTP）：带 middleware 的构建对 `/en/blog/best-solopreneur-acv-calculator/` 返回 **404，且没有 Location 头**。

修法：**新增 `src/pages/[lang]/blog/[...slug].astro`，`export const prerender = false`** —— 这条路由的作用不是"渲染一个页面"，而是**把 `/blog/*` 这段 URL 面挂到 Function 上**。挂上去之后 middleware 就会跑（实测 5/5 的 301 全部正确）。

⇒ 由此多出一条**承重墙断言**：这条路由一旦被改回预渲染，301 会**静默**失效（站点变 404，但没有任何报错）。所以守卫里单列一条钉住 `export const prerender = false`。

### 9.3 坑三：sitemap 的 filter 收到的是字符串，而且异常被吞

第一版 sitemap filter：

```js
filter: (page) => !SHELL_PAGE_RE.test(new URL(page.url).pathname),
```

`@astrojs/sitemap@3.2.1` 的 `.d.ts` 写得很清楚：`filter?(page: string): boolean`；实现里是 `pageUrls.filter(filter)`，而 `pageUrls` 是 `string[]` ⇒ **`page` 是 URL 字符串，`page.url` 是 `undefined`** ⇒ `new URL(undefined)` 抛 `TypeError: Invalid URL`。

而集成对 filter 抛出的异常是这么处理的：

```js
try { pageUrls = pageUrls.filter(filter); }
catch (err) { logger.error(`Error filtering pages\n${err.toString()}`); return; }
```

⇒ **记一条 error 日志，然后直接 return —— 一个 sitemap 文件都不写。而构建照样 exit 0。**

**实测**（`dist/` 里没有 `sitemap-index.xml`，也没有 `sitemap-0.xml`），而 `public/robots.txt` 仍然写着 `Sitemap: https://forgeflowkit.com/sitemap-index.xml` ⇒ 站点对外宣称有 sitemap，实际 404。

这类失败任何"看构建退出码"的门禁都看不见 ⇒ 加了 **build-dep 守卫 `tests/sitemap-shell-page-guard`** 盯住**产物本身**（文件存在 / 壳页不在其中 / 根 URL 的 hreflang 正确），并用真实回归（把 filter 改回读 `page.url`）重建一次验证：**构建绿、守卫红**。

### 9.4 顺带修掉的两个真 bug

1. **`yt-lang` cookie 从未被设置过** —— grep 全仓库只有 `src/pages/index.astro` 一处**读取**、零处**写入** ⇒ 旧代码 `m ? m[1] : "en"` 的兜底是唯一生效的分支：**每个访客（含中文用户）都被丢进英文首页**。改成「只有访客明确选过语言才自动跳转」。
2. **`Astro.rewrite('/404')` 会 500** —— 404 路由是**预渲染**的，服务端 bundle 里没有它的 page 组件 ⇒ 实测抛 `TypeError: module.page is not a function`（`AstroPipeline.getComponentByRoute`）⇒ 未知 blog URL 返回 500。改为直接返回 404 响应体（**必须是真 404**：200 + 404 页 = soft 404，Google 会把它当正常页面索引）。

### 9.6 守卫

| 守卫 | 类型 | 断言 | 变异台子 |
|---|---|---|---|
| `p155-structure-fix-guard` | source-only | 24 | **25/25 KILLED** |
| `sitemap-shell-page-guard` | build-dep | 3 | 真实回归（`page.url`）重建一次：构建绿、守卫红 |

> **变异台子抓到台子自己的 3 个 bug**（值得单独记一笔，因为它们都会让结论失效）：
> 1. **每轮变异前没还原** ⇒ 变异在文件上层层叠加，后面的每一轮都带着前面几轮的破损 ⇒ 连带红越来越多，"22/25 KILLED"这种数字是假的。还原必须发生在**每一轮开头**，而且要有 sha256 逐字节校验。
> 2. **正则提取把定界符吞进去了** ⇒ 造出来的正则源变成 `/^…$/` ⇒ 永远不匹配 ⇒ 守卫红在提取上，不在实现上。
> 3. **判据写得太松**：`new\s+Response\([\s\S]*?status:\s*404` 匹配到了文件里**更早**那个响应（lang 校验的），于是把真正那个响应的状态码改成 200 也照样绿 ⇒ 必须断**具体那个响应**（`new Response(body, { status: 404 … })`）。
>
> 另有一条更根本的：**文本判据抓不到"把条件改坏"**。第一版 sitemap 守卫只查 `filter: (…) => !SHELL_PAGE_RE.test(...)` 这个**形状**，于是 §9.3 那个真实回归 100% 逃逸。修法是把那个 filter 表达式**原样取出来当函数跑一遍**（`new Function('SHELL_PAGE_RE', 'return (' + expr + ')')`）—— 行为判据，不是形状判据。

| openai | FAQ[1] | GPT-5 Nano = `$0.05/$0.40` | `$0.05/$0.40` | ✅ 对 |

**比「单价漂了」更严重的是三类结构性错误**：

1. **比较方向写反了**（3 处）：gemini FAQ[0] 写「Gemini 3 Flash 比 Claude Haiku 3 **便宜 75%**」—— 实测 Gemini 3 Flash 的输出价是 Claude Haiku 3 的 **240%**（更贵，不是更便宜）。FAQ[4] 写「3.5 Flash 输出比 GPT-4o 便宜 10%」—— 实测是 **90%**（更贵）。这类错误**只看单价是发现不了的**，必须比对两个模型的相对关系。
2. **数量级错**（1 处）：claude FAQ[9] 写「200K prompt 是 $0.0003，1K 是 …」—— 200K token 的输入成本应是 **$0.60**，1K 是 **$0.003**，原文**两个都错**（`$0.0003` 是把「每百万价」当成了「每 K token 价」）。
3. **locale JSON 索引错位**（2 条）：`claude-api-cost-calculator` 与 `openai-token-calculator` 的 `en.json` 里，**FAQ[7] 与 FAQ[14] 重复**（都是最后一条）⇒ 引擎的第 7 条 FAQ 在 zh 页面上**整条消失**，取到的是第 14 条的内容。

⇒ **漂移比对必须三段式**（已在 agent memory 固化）：① **值**（数值不是字符串）② **归属**（紧邻的模型名 → 数据集里那个模型）③ **推导结论**（倍数 / 方向 / 区间是否随之作废）。只做①会同时高估（`0.3` vs `0.30`）和漏报（挂错模型）。

### 13.2 修法：FAQ 也走 token 化，但**解析发生在渲染层**

用户拍板的形态：**把 `resolveLiveTokens` 接到工具页渲染层**（`src/pages/[lang]/[slug].astro` 的 `translatedFaq`），**不改 calc 内部逻辑**。

为什么解析放在渲染层而不是引擎里：FAQ 的英文源在**引擎 .ts**，而中文在 **locale JSON** —— 两处都要解析，放在引擎里只能覆盖 en。`translatedFaq` 同时喂给 `<FAQ>` 组件和 `createToolFAQPage` 的 JSON-LD ⇒ **一次解析，两处都对**。

### 13.3 新增 token（6 种）+ 一个设计决策：为什么用「占比」而不是「便宜百分之几」

| token | 输出 | 用途 |
|---|---|---|
| `{{liveBatch:provider/key}}` | `$0.25 / $1.50` | 批处理价（数据集里 **39/245** 个模型有批处理档；没有就是 null，**不许显示 0**） |
| `{{liveBatchIn:...}}` / `{{liveBatchOut:...}}` | `$0.25` / `$1.50` | 只取一边 |
| `{{liveShareIn:A\|B}}` | `60%` | **A 的输入价是 B 的百分之多少** |
| `{{liveShareOut:A\|B}}` | `90%` | 同上，按输出价 |
| `{{liveShareMix:A\|B}}` | `6%` | 同上，按混合负载（1000 in + 500 out） |
| `{{liveCostIn:provider/key\|tokens}}` | `$0.60` | N 个 token 的输入成本 |
| `{{liveCostOut:provider/key\|tokens}}` | `$0.005` | N 个 token 的输出成本 |
| `{{liveCostMix:provider/key\|in\|out}}` | `$0.00625` | 一次请求的总成本 |
| `{{liveScaledIn:provider/key\|factor}}` | `$0.30` | factor × 输入价（**缓存折后价** 0.1x / 0.02x） |
| `{{liveMonthlyAt:provider/key\|reqs}}` | `$1.35` | 按每月请求数的月支出 |

⭐ **「占比」而不是「便宜百分之几」**：最初的实现让 token 返回 `"40% cheaper"` 这样的带方向短语。试过之后有两个硬伤：

1. **语言**：token 的返回值是**数据**不是模板 —— 同一份数据要同时喂 en 和 zh 两个页面。`"40% cheaper"` 塞进中文句子会变成「便宜 40% cheaper」。
2. **方向**：裸数字 + 编辑写死的方向词（「A 比 B 便宜 40%」）在价格顺序反转时会变成一句**彻底错误却无人报错**的话。

所以 `liveShare*` 返回**语言中立 + 方向安全**的占比：「A 的价格是 B 的 60%」。这个句子在两种价格顺序下都成立、都通顺，而且中英文用**同一个 token**：

```
en: "costs 60% of GPT-4o's input price"
zh: "的价格是 GPT-4o 的 60%"
```

⚠️ 跨多个模型的倍数（「便宜 5-20 倍」）**仍然无法用单一 token 表达** ⇒ 那些句子改成了**定性表述**（"a fraction of" / "一小部分"）。

### 13.4 范围界定：什么派生了，什么保留手写

| 类别 | 处理 | 理由 |
|---|---|---|
| 紧邻具名模型的每 1M token 价 | ✅ **全部派生**（28 条 FAQ） | 数据集 `llm` 段能给出 |
| 两个模型之间的比较 | ✅ **派生**（`liveShare*`） | 否则方向会写反 |
| 由实时价算出的派生价（缓存折后价、单次请求成本、月支出） | ✅ **派生** | 否则数量级会错 |
| 图片单价（`$0.0015/image`）、视频/音频每秒价 | ❌ **保留手写 + 白名单** | 按次计费，不是 token 单价 |
| embedding 单价（`$0.02/1M`）、微调单价（`$3/1M`） | ❌ **保留手写 + 白名单** | 数据集的 `llm` 段**没有** embedding / 微调模型 |
| 预算经验区间（`$0.001-0.01`、`$150-1500`）、启动额度（`$5K-$25K`） | ❌ **保留手写 + 白名单** | 聚合支出 / 云厂商政策，不是模型单价 |

**白名单不是「免责区」**：每条白名单都必须写明理由，且**必须仍在文本里出现**（否则白名单已腐烂 ⇒ 守卫会红）。

### 13.5 守卫

- `engine-faq-live-price-guard`（source-only，**7 条**）：① FAQ 里不再有手写的「每 1M 单价」（白名单除外）② 每个 token 都能解析（key 必须在数据集里）③ **三处同步**（引擎 / en.json / zh.json 逐条对齐，**且三处的 token 集合必须一致**，**且 en.json 的问题不得重复** —— 后两条是本轮新加的，用来钉住 §13.1 的索引错位）④ token 数量下限 + 关键价格钉死（防「把价格全删掉」钻空子）⑤ 名实一致（防「名字指 A、价格指 B」）⑥ 各 token 类型的派生值 == 写死字面量 ⑦ 白名单不腐烂。
- `engine-faq-live-price-build-guard`（build-dep，**3 条**）：全站 `dist/` 里没有未解析的 `{{live*}}`；5 个引擎的 en + zh 页面都渲染出了**引擎源** FAQ 的**解析后**文本；页面上的价格 == 数据集实时值，且**修掉的过期价格串已消失**。
- **三个既有守卫必须改成「解析后再比对」**：`engine-en-faq-i18n-guard` / `engine-zh-faq-i18n-guard` / **`engine-faq-html-render-guard`** 都要求 FAQ 的文本**逐字出现在** `dist/` 的 HTML 里 ⇒ token 化之后原文必然找不到 ⇒ 必须先 `resolveLiveTokens` 再比对。**这三条不解决，守卫必红。**（第三个守卫是全量跑套件时才发现的 —— 只改了前两个就以为完事，结果 CI 红了。⇒ **「同一类断言」要一次找全，不能靠撞红来发现。**）
- ⭐ **修第三个守卫时挖出一个更老的覆盖盲区**：`engine-faq-html-render-guard` 的提取正则**只匹配双引号条目**（`q:\s*"..."`）⇒ 全站 **1322 条 FAQ 里只有 814 条进过这个守卫**，**508 条（38%）从来没被检查过**（单引号条目不是「不存在」，只是正则没看见 —— 而「没看见」等于「没保护」）。修法：提取正则改成单/双引号都匹配 ⇒ 覆盖 **814 → 1322**，且 508 条新纳入的条目**全部渲染正常**（零新增违规）。⇒ **正则写得越窄，守卫看起来越绿；覆盖率本身需要一个数字来盯。**
- 变异台子：`tmp/mutate-engine-faq-price.mjs`（source-only，**9/9 KILLED**）+ `tmp/mutate-engine-faq-price-build.mjs`（build-dep，**3/3 KILLED**，真重建后红）。每轮**开头**还原 + sha256 逐字节校验，收尾也还原并校验。

⚠️ **变异台子本身踩了两个坑，都是「台子比守卫更不可信」的形态**：

1. **进程被 kill 时 `finally` 不会执行** —— 一次工具超时把台子杀在 B1 变异之后，文件**永久停在了变异状态**（`q:` 行的解析器丢了），下一轮台子拿到的 `ORIGINAL` 就是坏的 ⇒ B1 锚点「命中 0 次」，而我一度以为是守卫的漏洞。⇒ 台子必须：跑之前把**快照落盘**、启动时若有遗留快照**先还原**再捕获 `ORIGINAL`、再注册 `SIGINT/SIGTERM/SIGHUP` 处理器。
2. **无效变异（no-op）看起来像「守卫没抓到」** —— 第一版 B1 改的是 `q:` 行，而 FAQ 的**问题里根本没有 token**（token 全在答案里）⇒ 移除 `q` 的解析器是个 no-op ⇒ 守卫当然抓不到。⇒ **变异必须先确认它真的改变了行为**，否则「SURVIVED」这个结论是错的。

⚠️ **变异台子抓到了一个真漏洞**：第一版的守卫只比对 en.json 与引擎源，**没比对 zh.json 的 token 集合** ⇒ 变异 M4（zh.json 两条 FAQ 互换）**存活**。修法是把「三处的 token 集合必须一致」写进守卫 ③ 之后 M4 才 KILLED。⇒ **守卫的断言要按「失败模式」逐条设计，而不是笼统地「比对一遍」。**

### 14.2 修法：GPU 也走派生，编辑口径对齐数据集的 6 家

`src/lib/live-price.ts` 新增 **21 种 GPU token**（读 `ai-pricing.json` 的 `gpu.providers`），把「谁家、哪个型号、哪个档位、多少钱」全部交给数据集：

- 名单与家数：`{{liveGpuProviderCount}}` / `{{liveGpuProviderList}}` / `{{liveGpuProviderName:provider}}` / `{{liveGpuTypeList}}` / `{{liveGpuTypeCount}}`
- 单价：`{{liveGpuRate:provider|type}}`（按需）/ `{{liveGpuSpot:...}}`（现货）/ `{{liveGpuReserved:...}}`（预留 1 年）
- 区间与折扣带：`{{liveGpuRange:type}}` / `{{liveGpuSpotRange:type}}` / `{{liveGpuOffSpot}}` / `{{liveGpuOffReserved}}`（带）/ `{{liveGpuOffSpot:provider}}`（单家）
- 相对关系：`{{liveGpuShare:A|type|tierA|B|type|tierB}}`（占比）/ `{{liveGpuRatio:...}}`（倍数）
- 月账单：`{{liveGpuMonthly:provider|type|tier|gpus|hoursPerDay}}` / `{{liveGpuMonthlyRange:...}}` / `{{liveGpuMonthlyBlend:...}}` / `{{liveGpuMonthlyBlendRange:...}}` / `{{liveGpuBlendBand:type|r|s}}`
- 归属：`{{liveGpuCheapest:type|tier}}` / `{{liveGpuPriceiest:type|tier}}`

⚠️ **编辑口径删掉了 CoreWeave / FluidStack / Crusoe / OCI** —— 它们在数据集里没有价格，留着就只能靠手写（而手写正是漂移的来源）。这不是「少写了几家」，是「不发布没有真相源的事实」。

### 14.3 两个设计决策（都是「写死的归属会变成一句彻底错误却无人报错的话」）

1. **`min` / `max` 两个假 provider 名**：`{{liveGpuShare:min|H100|on|max|H100|on}}` 表达的是「该型号 + 该档位下最便宜的供应商 vs 最贵的」。如果编辑直接写死 "Vast.ai" / "AWS"，那么数据集里价格顺序一反转（例如 AWS 降价到 Vast.ai 以下），这句话就会变成彻底错误的断言，而**没有任何守卫会红**。
2. **`share` 与 `ratio` 的方向相反**：`share` 返回「A 是 B 的百分之多少」，`ratio` 返回「B 是 A 的多少倍」⇒ payload 顺序恒为「**便宜方在前**」。这一条是被渲染检查抓出来的：初版把 `{{liveGpuRatio:aws|H100|on|vastai|H100|on}}` 写成「AWS 是 Vast.ai 的 0.4 倍」（方向反了），应当是 2.4 倍。

### 14.4 范围界定：什么派生了，什么保留手写

- **派生**（数据集拥有的一切）：供应商名单与家数、型号清单、按需/现货/预留单价、折扣带、月账单、混合档占比。
- **保留手写 + 白名单**（数据集**不**拥有、但**带金额**）：出口流量的市场区间（$0.05-$0.12/GB）、10TB 跨区出口的示例金额（$900/month）、**计算器自己的**建模假设（存储 $0.10/GB、出口 $0.08/GB），以及由这些假设算出的月费（$50、$4）与合计（$2,905.20 —— 守卫会**独立重算**它）。白名单每条都写明理由，且**必须仍然出现在文本里**（白名单腐烂 = 红）。
- **降级为定性**（数据集**不**拥有、且**带金额或带折扣带**）：

### 17.2 契约：customFn 是**函数体**，不是「run 函数」

页面的代码是 `new Function('inputs','pick','fill', body)` 之后**直接调用函数体** ⇒ body 必须**自己执行并返回**。⇒ 契约对 100 个引擎统一：**顶层必须有 `return run(inputs, pick, fill);`，返回值必须是非空字符串数组**（页面只渲染 `results[0]` 并对它做 HTML 转义）。

**为什么不在 astro 侧加兼容 shim**（例如「有 `.run` 就调 `.run`」）：那样契约就变成「两种 body 都合法」⇒ 守卫必须同时认两种形态 ⇒ 复杂度翻倍，且**新写的引擎仍然会写成只有 `run()` 的形态**（M3 那一类整整齐齐 21 个就是这么来的）。把契约收紧在引擎侧 ⇒ 100 个引擎一个形状，且**可以被一条守卫强制**。

### 17.5 定价 bot 的 PAT

`action_required` 的成因：head 分支是用 `GITHUB_TOKEN` 推的 ⇒ 该 PR 的 `pull_request` 事件创建的 workflow run 会**等待维护者批准**并报告 **0 个 job**（实测：PR #4，run `41377087077`，`status=completed` / `conclusion=action_required` / `jobs=0`）。

## 19. P166：定价 bot 闭环 + B2 形态定案（修复优先级表 / 达标清单 · 试点 3 个）

> 本节对应计划：`docs/superpowers/plans/2026-11-03-p166-pricing-bot-closure-and-topic-priority-tables.md`。
> **宪法红线**：本批 `src/engines/**` **一个字节未动**（连注释都没有）—— 因为 bot 一旦改变策展侧的数量，就会撞上 `tests/ai-cost-scope-guard.test.ts` 写死的 18/13/8/5 = 44 与引擎静态文案「Cost Comparison (18 Models)」。策展是**人的决定**，不是 bot 的。

### 19.1 ⭐ 取证：每周必红的 PR，从未被任何人看见

三段取证串成一条链：

1. **数据集在涨，交互态不动** —— `scripts/sync-pricing.mjs` 只写 `src/data/ai-pricing.json`（数据集），而 `src/data/ai-pricing-popular.json` 决定「哪些模型进交互态」。两者之间**没有任何一步** ⇒ 新模型静默地只进数据集、不进交互态，用户在计算器里根本选不到它。
2. **唯一的信号是坏的** —— 唯一会因此变红的东西是 `popular-models-rule-guard` 里的**写死计数**（245 / 44 / 201 / 42）⇒ 它每周必红。但 PR #4 的 CI run **#317 至今是 `action_required`（0 个 job）** ⇒ 「每周 PR 必然红」这件事**从来没有被任何人看见**。
3. **供给侧在加速** —— 实测 2026-11-02 那周的同步就把 2 个新模型（`openai/gpt-6-rosalind`、`openai/gpt-6-astra-law`）带进了数据集（245 → 247）。

⇒ 缺口不是「还没修」，而是**从未被观测到**。这正是 P163「发现机制缺失」的第三次复发：**没有一条自动执行的路径回答「新模型要不要进交互态」**。

### 19.2 ⭐ 决策一：bot 永不碰策展侧（策展是人的决定）

bot 只做**排除侧**的决定，且默认方向是「排除」：

| bot 会做的（6 种行为） | bot 绝不会做的 |
|---|---|
| 新模型默认进排除清单（附族规则） | ❌ 改 `popularModelKeys`（策展侧） |
| 把新模型挂到**已存在的**排除族下 | ❌ 把新模型**提升**进交互态 |
| 为新模型**新建**精确匹配的排除族 | ❌ 改任何引擎的静态文案 / 模型数 |
| 剪掉已不存在的陈旧排除记录 | ❌ 改价格数据集 |
| 剪掉不再命中任何 key 的**死族** | |
| 策展模型从数据集消失时**拒绝写文件并 exit 1** | |

⇒ 最后一条是刻意设计的：**宁可不开 PR，也不替人做策展决定**。bot 遇到「策展里的某个模型从数据集消失了」⇒ 它不知道该留还是该删 ⇒ 那是人的决定 ⇒ bot 拒绝写入、让 job 失败、把问题摆在 job summary 里。

⇒ 同理，**引擎层一个字不动**：`popularModelKeys` 保持 44（openai 18 / anthropic 13 / google 8 / deepseek 5），排除侧保持 201，42 个排除族。

### 19.3 bot 的实现要点：外科式 JSON 写入 + 「没变就不写」

- **无正则的 glob 匹配器** —— bot 自己实现 `*` 分段匹配（与 `src/data/ai-pricing-popular.ts` 的 `matchesExcludedFamily` 语义等价）。等价性不是靠「读代码觉得对」，而是**在真实的 42 族 × 245 key 上逐例断言**（**10,290 对**，自测实测）。
- **外科式 JSON 写入**（`serializePreserving`）—— 只重序列化**真变了**的顶层成员 ⇒ `crossProviderModels` 段不会被重排 ⇒ 每周 PR 的 diff 里**只有真的决定**，没有与策展无关的噪音。
- ⭐ **「没变就不写」是「不开空 PR」的前提** —— `_rule.updatedAt` 的语义是「**决定是什么时候做的**」，不是「价格什么时候同步的」。⇒ **只有决定集真变了才写运行日期**；没变就保持原值。第一版没做这件事 ⇒ 每周都产生一个内容没变的 `popular.json` diff ⇒ **每周开一个空 PR** ⇒ 这是本批修掉的一个真实回归（自测里补了对应断言，且该断言已证明非空转）。

### 19.4 守卫改造：从「写死精确值」到「floor + 三条恒等式」+ 一条接线守卫

| 守卫 | 职责 | 形态 |
|---|---|---|
| `popular-models-rule-guard` | 数据层：策展 ∪ 排除 == 数据集全集（且互斥）· 声明值 == 实际值 · `_rule.datasetModelCount == datasetTotal()` | source-only |
| `pricing-bot-wiring-guard` | **接线层**：bot 有没有被真的接进 workflow | source-only |

⭐ **为什么把写死计数改成 floor + 恒等式**：写死的 245 / 44 / 201 / 42 有一个致命的性质 —— **数据集一变它就红，而红的原因和「规则被破坏」完全无关**。⇒ 它不是一条守卫，它是一个**每周准时报错的噪音源**。⇒ 改法：floor 只挡灾难性塌缩（200 / 44 / 30），完整性交给**三条恒等式**：

1. **声明值 == 实际值** —— `_rule` 里写的计数必须与文件里真有的条目数一致；
2. **策展 ∪ 排除 == 数据集全集**（且互斥）—— 新模型两边都没进就红 ⇒ **这是完整性守恒**；
3. **`_rule.datasetModelCount == datasetTotal()`** —— 这是「**bot 跑过了吗**」的**探测器**：数据集变了而它没跟上 ⇒ 红。

⚠️ 每条断言只守一件事；期望值全部是**独立写死的字面量**，不从被测模块导出。

⭐ **接线守卫的粒度纪律**：`pricing-bot-wiring-guard` 的 4 条断言**各自落在 workflow 文件的对应片段上**（执行步骤 / 变更检测 / `git add` / `push.paths`）。**整页 grep `ai-pricing` 是不合格的** —— `paths:` 里本来就有 `ai-pricing.json` 了 ⇒ 整页查会误判「已接线」。这与 P165「按作用域查，不按整页查」是同一条纪律。

### 19.5 ⭐ 计划改案：拆 `topic-content.ts` 会连带改两处

原计划把 `src/data/topic-content.ts`（**2,900 行 / 980 KB** 单文件）拆掉，新形态直接进去。**执行前取证发现它不能拆**：

- `scripts/audit-gemini-extractability.mjs` 用 `txt.indexOf('export const TOPIC_GUIDE_CONTENT:')` **切块** + 正则抓主题 ⇒ 拆文件会让审计脚本**悄悄少报几个主题**（不是报错，是**少报** ⇒ 更危险）。
- `src/data/price-claim-surface-ledger.ts` + `tests/price-claim-surface-ledger-guard.test.ts` 也**按文本解析**它。

⇒ 改案：新形态放**独立的一层** `src/data/topic-priority/`，`topic-content.ts` **一个字节都不改**。附带收益：**一主题一文件** ⇒ 下一批铺其余 42 个主题时**天然可并行、互不冲突**（这正是 P165 在决策层上吃到的甜头）。

### 19.6 ⭐ 形态定案：为什么是「修复优先级表 / 达标清单」

P165 把 B2 定成「定位表 + 门槛清单」。**执行前取证把它改案了**：

- 基准页的 `howToUse`（单指标 → 单动作）**就是**「定位表」要表达的「我落在哪一档」；
- 指南页的 `howToApply`（Step 1..N 编号链）**就是**「门槛清单」要表达的「先做哪一步」；
- ⇒ 再加这两样 = **把已有散文抄一遍** = 站内自我重复（与 2.0「产出必须是页面独有结论」正相反）。

⇒ 真缺口是这两个**在任何现有段落里都不存在**的问题：

| 形态 | 回答的问题 | 与已有内容的区别 |
|---|---|---|
| **修复优先级表**（基准页） | **多个指标同时不达标时，先修哪个？** | 已有内容是「单指标 → 单动作」；这里是**多指标排序 + 联动（改 A 会顺带动 B）+ 反噬（先修 A 会不会让 B 更糟）** |
| **达标清单**（指南页） | **每一步做到什么程度才够？不够卡在哪？** | 已有内容是「Step 1 做 X」；这里是**每步的达标线 + 不达标的后果（blockIf）** |

⇒ 两个形态的字段因此不同：修复优先级表 = `priority` + `metric` + `fixFirst` + `alsoMoves` + `backfire`；达标清单 = `step` + `label` + `gate` + `blockIf`。

### 19.7 渲染层：仅当数据存在才渲染 ⇒ 非试点页产物字节不变

两个 astro 模板按「该主题**有没有**新形态数据」决定是否渲染新区段：

- 基准页 `[topic]-benchmark.astro` → 5 列「修复优先级表」；
- 指南页 `[topic]-guide.astro` → 4 列「达标清单」。

⭐ **条件渲染是本批的关键设计**：不存在的**连 H2 都不出** ⇒ 其余 42 个主题的产物**逐字节不变** ⇒ 本批不会污染站点的其余部分。且这条不是靠约定保证，而是由 build-dep 守卫**正面**断言：「非试点主题的页面**不得**出现新区块」。

⭐ **i18n 新增 12 个 key**（计划写 9 个 —— 因为 `step_n` 用参数化复数，实际需要 12 个）。en / zh 各 **5,160** 键、两语言集合**完全对齐**，`check-i18n-completeness.mjs` 通过。

### 19.8 价格纪律：按主题分档（规则不得比需求更严）

⚠️ 本批的一条真实教训：**规则比需求更严会把编辑逼向错误形态**。扫描工具最初把**任何** `$` + 数字都判为「手写单价」⇒ 逼 C 类主题把金额写成别扭的「USD 300-1,500」⇒ **内容形态被工具的错误规则扭曲**。⇒ 改为**按主题分档**：

| 档 | 主题 | 纪律 |
|---|---|---|
| **严格** | B 类（`llm-api-cost-optimization`）—— 讲的是**模型单价** | 所有单价**必须**走 live token（手写价格每周随 bot 漂移） |
| **宽松** | C / R 类 —— 讲的是**用户自己的经营阈值** | 允许手写，但必须**标明口径**（如「USD 300-1,500 / 月」） |

⇒ 实测：B 类主题 **22 个 live token、0 个手写 `$` 金额**。
