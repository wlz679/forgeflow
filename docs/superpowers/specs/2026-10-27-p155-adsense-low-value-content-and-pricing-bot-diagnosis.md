## 3. 结论（条件式，不是一句「会好很多」）

**「2.0 灵魂改造会不会好很多」取决于它落在哪一侧。**

- **落在模板侧 → 可能更糟。** Google 对工具站的 "low value content" 判定，核心信号之一是**页面间差异度不足**。437 页各加一段结构相同的第 N 个板块 = 内容量 +、独特性比率 − → 相似度更高 → 对判定更不利。
- **落在独特侧 → 正杠杆。** 维度 1（Decision Support System）+ 维度 3（Proactive Co-Pilot）的本意正是「每页产出**页面独有**的结论」：真实行业阈值、跨引擎对比、基于用户输入算出的建议 —— 这类内容天然独特。

**分界线是「独特内容比例」，不是「内容总量」。**

**但更可能的主因不在内容。** AdSense 对中小站的 "low value content" 大量是**流量/广告库存价值**判定，而不是内容判定 —— 一个每天几百 PV 的站，即使内容再好也难通过。**这一点必须先取证再决定改不改**，否则会拿整站重写的成本去赌一个未验证的假设。

### 3.1 时序上有一个被忽略的事实

复审窗口 **10-19 → 10-27**，而**死链修复（98 个死链目标 / 586 处断链）是在 10-23 10:53 上线的**（`21bf890`）。⇒ **窗口前 4 天（10-19 → 10-23）的抓取看到的是带 586 处断链的版本**，后 4 天可能是修复后的。所以"审核抓到了断链"这件事**成立但不覆盖整个窗口**——不能全归到断链头上，但也不能假定抓到的都是修复后的版本。

现在站点是 0 断链 + ads.txt 已授权，**比送审时更好** ⇒ **正确的第一步是申请重新审核**，成本远低于重做内容。

## 6. 同期修复：每周定价 bot 的 "Open or update Pull Request" 步骤

### 6.1 定位（不靠猜）

GitHub API 匿名可读，实测：

- `chore/pricing-sync` 分支**存在**，head `092add0`，父提交 = master 的 `4013863` ⇒ **领先 master 1 个提交**（差异只有 `src/data/ai-pricing.json` 1 行）⇒ 不是"没有可提的提交"。
- `head=wlz679:chore/pricing-sync` 的 **PR 数量 = 0** ⇒ `gh pr create` **没有建出 PR**。
- 仓库历史上只有 2 个 PR（2026-06，均为人工创建且已关闭）⇒ **bot 从未成功建过 PR**。
- job 权限：`contents: write` + `pull-requests: write` **都在** ⇒ 不是 token 作用域缺失。
- 失败步骤 = "Open or update Pull Request"（第 11 步，含 "Set up job" 计数），前面的 Sync / Regenerate / Commit / Push branch 全绿。

### 6.2 旧写法有两处结构缺陷

1. `gh pr view "$BOT_BRANCH" ... 2>/dev/null` —— **stderr 被直接丢掉**。gh 的真实报错（403 / 权限 / 配额 / 参数错）一行都不会出现在任何地方，只剩一个裸的 `exit code 1`。
2. 用 `gh pr view` 的**退出码**当"有没有 PR"的判据 —— gh 在"没有 PR"和"API 拒绝访问"两种情况下的退出码无法区分 ⇒ "API 报错"会被误判成"没有 PR"，继而走进 `gh pr create`，再撞一次墙。

**这也解释了为什么这次排查取不到日志**：job log 需要登录态（GitHub 未认证访问返回 403），公开 API 只能证明"分支推了、PR 没建"。

### 6.3 修法

- 诊断写进 **job summary**（Actions 页面直接可见，不需要读 log）：`gh auth status` + `repos/$REPO/actions/permissions` + `repos/$REPO/actions/permissions/workflow`（后者的 `can_approve_pull_request_reviews` 正是"仓库是否允许 GITHUB_TOKEN 建 PR"的那个开关）。
- 存在性判定改用 **API 列表** `pulls?state=open&head=owner:branch`（空数组 = 没有 PR，非零退出 = API 真的报错）。
- 创建/更新后**用 API 回读确认** PR 真的可见，确认不了就非零退出。
- 创建失败时**留下人工可点的 compare 链接** —— 分支已经推了，一周一次的定价增量不该因为建不了 PR 而静默丢掉。

### 6.4 守卫

`tests/sync-pricing-pr-step-guard.test.ts`（source-only，7 条断言）钉住上面 5 条性质。变异台子 **7/7 KILLED**，还原后 sha256 逐字节一致。

> 变异台子抓到守卫自己的两个漏洞：
> 1. 第一版只查 `VERIFY_URL` 这个标识符，删掉赋值行、只留 `if [ -z "$VERIFY_URL" ]` 时仍然恒绿。已改成断**读取动作本身**（`VERIFY_URL="$(gh api … pulls?state=open`）。
> 2. 第一版把 `head` 过滤写成 `owner/repo:branch`。**实测真实 API 不报错** —— 两种写法都返回 HTTP 200 + 空数组，即错误写法**静默声称"永远没有 PR"**，步骤就会走进 `gh pr create` 撞上 "a pull request already exists"。已改用 `$GITHUB_REPOSITORY_OWNER`，并单列一条断言钉住。
