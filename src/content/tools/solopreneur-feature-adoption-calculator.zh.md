## 这个计算器衡量什么

功能采纳率衡量在特定时间窗口内，「活跃用户中有多少实际使用了
某个功能」。它直接回答 PM 最关心的问题：「本可以用这个功能的
人里，有多少真的用了？」——和「使用频率」（重度用户多频繁打开）
或「满意度」是不同的维度。一个 25% 采纳率的功能可能是高价值
资产；一个 5% 采纳率的功能多半是死重，应当重新定位或下线。

## 计算方法

我们使用的 v3 标准公式：

```
功能采纳率 = 功能用户数 / 活跃用户数
```

| 变量          | 含义                                                          |
| ------------- | ------------------------------------------------------------- |
| `功能用户数`  | 在该周期内触发功能事件的去重用户数                            |
| `活跃用户数`  | 总去重活跃用户（WAU 或 MAU，按下拉选择）                      |
| `未采纳数`    | `活跃用户数 − 功能用户数`——本可以用但没用上的用户             |

社区基准下的健康带：绿 ≥40% · 黄 20–40% · 橙 10–20% · 红 <10%。
分母选择很关键：WAU 体现活跃用户群中的使用深度（更严格的测试）；
MAU 体现整体覆盖面。决定使用深度时用 WAU，决定优先级排序时用 MAU。

## 局限性 / 何时不适用

采纳率衡量的是**是否**用过，不是**多喜欢**。一个 60% 采纳率的
功能可能只用一次再没回来——这是有采纳没价值。要配合使用频率、
功能维度的留存 cohort 来确认功能确实在推动粘性。在 B2B 产品中，
采纳率还受基于角色的访问控制影响——不能编辑工作流的管理员不会
出现在功能采纳计数里，即使他们受益于输出。先核对事件埋点定义：
如果「功能使用」在自动加载时触发而不是用户主动行为，采纳率会被
虚高到 100% 以上。

## 案例走读

某中型 SaaS 上线了「保存视图」新功能，PM 想看它是否站稳脚跟。
从 Mixpanel 看，过去 30 天有 750 个去重用户触发了保存视图事件，
活跃用户共 3,000 人（WAU）。

1. `功能采纳率` = 750 / 3,000 = **25.0%**（黄带——健康，仍有空间）。
2. `未采纳数` = 2,250 人——他们是优化目标（已活跃却没用此功能）。
3. What-If：转化 10% 未采纳用户（额外约 225 人），采纳率可提升到约 32.5%，逼近绿带。
4. Break-Even：Excellent（40%）要求 3,000 WAU 中至少有 1,200 人使用。20% 的 Good 阈值（600 人）已经跨过。
5. Milestone：本季度内通过在新手引导邮件里露出此功能，把采纳率提升 +10 个百分点到约 35%。配合 **Activation Rate Calculator** 区分「用过一次」与「反复回来」的两类用户。
